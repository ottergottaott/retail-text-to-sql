Assessment MVP · see acceptance boundaries
01 / System boundaries

One backend. Thin clients.

These are logical components, not independently deployed microservices. Open WebUI provides the chat experience; the API owns every product operation.

Application state stores conversations, reports, user preferences, feedback, versions and index records. Raw transactions stay in BigQuery. DuckDB is used only for synthetic offline SQL fixtures.

02 / Request lifecycle

Planning can loop. Execution stays bounded.

Authorized context→Structured decision⇄Trusted tool→Draft→Grounding review→Answer / save

Typed decisions, explicit dispatch

The model returns a validated JSON Decision, such as action=query. This is not native provider tool calling. The graph dispatches query/report/preference actions and returns their real results to the next model call.

A sanitized SQL resolution error may be repaired once. Query, model-call, elapsed-time, byte and row limits bound the turn. Ambiguous metrics can stop at clarification.

Evidence before persistence

Live analytical drafts undergo one final grounding revision against original SQL/results and trusted scope. A stronger reviewer is optional. A failed review saves no completed draft.

Saved reports are independent records. HTML Artifacts and the authenticated Reports library reopen them without repeating the underlying analysis queries.

03 / Retrieval

Retrieve methods. Query current facts.

Scope first, ranking second

Only the latest permitted published Trio with a compatible schema can enter retrieval. Text overlap and metadata scores combine with embedding ranks through reciprocal rank fusion. The lexical component is not BM25.

With compatible vectors, lexical candidates require cosine similarity ≥0.60; semantic-only candidates require ≥0.65. Missing current vectors cannot resurrect stale examples. Provider failures use explicitly labeled lexical fallback.

Versioned, explicit indexing

A Trio contains Question → SQL → Analyst Report. Examples teach definitions and analytical methods; their historical numbers are not current evidence.

Index identity binds provider/model, dimensions, instruction, content and source version. Operators index approved documents explicitly; user questions only create a query embedding. Bundled examples are synthetic.

04 / Security and reliability

The model does not own authorization.

BoundaryImplementation
Identity and ownershipThe WebUI server forwards its verified identity using a private adapter credential. Reports, conversations and feedback are checked against owner and current product entitlements.
SQL and PIIsqlglot validates a restricted read-only logical schema. Trusted source binding restricts every physical source to authorized brands (CEO: all brands). Demographics use grouped SQL and a minimum distinct-customer cohort; raw demographic listings fail closed. Raw customer names/contacts are absent from the model-facing schema; disclosure checks add another layer.
DeletionThe agent proposes exact owned targets. A separate explicit user confirmation checks owner, conversation, target versions and expiry before deletion.
Failure behaviorNo invented success on timeout/provider failure. Save receipts follow actual persistence. Interrupted clients are told to inspect saved state before retrying mutations.
ObservabilityRequest/turn/tool correlation, stage timings, versions, outcome, sanitized error categories, query jobs/bytes and measured provider tokens. Optional Langfuse export; no prompt/raw-row export. Monetary cost remains unavailable when not returned.
05 / Continuous improvement

Personal preferences. Evaluated shared knowledge.

User-level loop

My preferences saves explicit format/depth per user and loads them into every new turn. Reset creates a new version. The design applies inferred preferences automatically with user override/reset. Automatic inference and chart preference remain design scope.

Give feedback binds to the actual owned response snapshot. A revision guard rejects stale regenerated answers. Ratings/comments remain unreviewed; native WebUI thumbs are not bridged.

System-level loop

Feedback→Operator candidate→SQL cases→Evaluation gate→Publication / index

The current optional demo uses an operator-reviewed publisher. The production design automatically promotes low-risk examples after evaluation; human review handles exceptions. Failed evaluation blocks publication. New versions retain provenance. Rollback republishes a reviewed prior method as a new version. No autonomous training or hidden background learning service.

06 / Evaluation and extension

Different claims need different checks.

What was measured

252 controlled regression tests passed; current brand/privacy changes await a new live Gemini run. Separate live BigQuery checks compare business results against independent SQL references. Retrieval uses Recall/Precision/MRR/nDCG and negative-match rates.

Ragas whole-response and custom SQL-aware factual judges are reported separately. Neither score is an overall answer-accuracy percentage. A real-model learning demo verifies one new definition using fixture SQL.

Inspect evidence and remaining gates →

Where the design can grow

Dashboards can reuse the authorized query executor and report renderer. Scheduled refresh needs a persisted analysis definition, trusted scheduler identity, execution records and freshness policy.

Dynamic schema discovery, a nondeveloper review queue, OIDC, managed storage, durable workflow resume and production retention remain extensions, not implemented services.

Local acceptance: host API + SQLite and Docker WebUI; Compose also provides an API/PostgreSQL/WebUI demo. This is an MVP, not a claim of production readiness. Human report acceptance, fresh-machine setup and optional live Langfuse ingestion remain open.
